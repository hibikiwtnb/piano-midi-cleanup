## 1. GUI 内需要就地操作提示

目前部分操作只有看 README 才能知道，这不合适。基础操作应该在软件内部就能被发现。

典型例子：`第一拍位置（秒）` 输入框获得焦点后，可以用方向键微调，但界面本身没有提示。

建议：

- 不一定做完整帮助页面。
- 对这种简单操作，在控件附近显示轻量浮动提示即可。
- 视觉感觉可参考现有和弦代号的浮动小窗。
- 提示必须非常短小，大约 2～3 行、每行约 4～5 个字。
- 只写关键操作，不写成长说明。

示例：

```text
方向键
微调位置
```

README 只能作为补充文档，不能承担基本操作教学。

## 4. Piano Roll 需要基础音符编辑

当前界面没有办法直接删除特定音符或修改其所属手。

希望加入最简单的框选编辑：

- 鼠标拖框选择一个或多个音符。
- 按 `D`：删除所选音符。
- 按 `C`：切换所选音符所属的手。
- 三手 / 四手模式下，连续按 `C` 循环切换所属手。
- 每次切换后音符颜色立即变化，让用户直观看到当前所属手。

不要求复杂编辑器功能，先满足“框选、删除、换手”。

## 6. 版本管理侧边栏：比较语义需要重新整理

最新版本增加了版本管理侧边栏，但比较结果中的“漏音 / missing”等语义容易产生误解。

核心问题：

如果 B 相对于 A 少了某个音符，这个音符可能是：

- 程序按照规则主动删除的；
- B 自身真正漏掉的；
- A 本身多出来的；
- 两个版本都不是本程序生成，只是双方本来就不同。

不要尝试用复杂规则自动判断“到底是真的漏音还是规则删除”。这会把问题越做越复杂，而且不可靠。

### 推荐原则：使用对称、方向明确的差异表达

不要直接写“漏音”。应该明确是谁相对于谁：

```text
A 有、B 无
B 有、A 无
```

或其他等价、对称、没有原因推断的表达。

对于任意两个版本比较，都应该能够同时表示双方各自独有的音符，而不是默认其中一方是“正确版本”。

### 需要重新考虑展示结构

这一块可能需要用一个简单的对照表或双向结构，才能让关系一眼明白。

重点是：

- 明确比较方向；
- 不推断缺失原因；
- 不把程序主动删除直接叫做“漏音”；
- 支持两个外部版本互相都有独有音符的情况。

希望：

- 提示必须非常精简。
- 不能明显挤占侧边栏空间。
- 文案和布局需要仔细把握，不要为了“帮助”把侧边栏做得更复杂。

## 8. Review 阶段也必须更新版本号

最近多次较大的功能性改动没有同步修改版本号，导致 Review 时无法准确说明“具体是哪个版本的问题”。

以后每次较明显的功能改进都必须同步更新版本号，即使仍在 Review 中。

建议规则：

```text
Review 中：
1.0.1 → 1.0.2 → 1.0.3

用户确认该阶段修正 OK 后：
→ 1.1.0
```

也就是说：

- Review 期间每一轮可识别的功能改动，至少提升最小一级版本号。
- 用户明确确认该阶段修改 OK 后，再升格为正式的较大版本。
- 目标是让每一轮反馈都可以准确绑定到一个版本号。
